## 1. Comandos base que vas a usar todos los días

|Comando|Qué hace|
|---|---|
|`git status`|Muestra qué archivos cambiaste y en qué estado están|
|`git switch <rama>`|Cambia a otra rama (versión moderna de `git checkout <rama>`)|
|`git switch -c <rama>`|Crea una rama nueva y te cambia a ella (versión moderna de `git checkout -b`)|
|`git pull origin <rama>`|Trae y aplica los cambios más nuevos de esa rama en GitHub|
|`git add <archivo>` / `git add .`|Prepara archivos para el commit|
|`git commit -m "tipo(alcance): descripción"`|Guarda un punto en la historia con esos cambios|
|`git push origin <rama>`|Sube tu rama a GitHub|
|`git log --oneline`|Ve el historial de commits, uno por línea|
|`git diff`|Ve línea por línea qué cambiaste y aún no guardaste|
|`git branch -a`|Lista todas las ramas, locales y remotas|

## 2. Flujo diario completo, paso a paso

### Paso 1: Antes de empezar cualquier tarea, actualizar `develop`

```bash
git switch develop
git pull origin develop
```

Nunca empieces una rama nueva desde una copia vieja de `develop`.

### Paso 2: Crear tu rama de trabajo

```bash
git switch -c feature/ventas-checkout
```

(Usa el prefijo y nombre que corresponda según la Guía de Ramas.)

### Paso 3: Trabajar y revisar qué cambiaste

```bash
git status
git diff
```

### Paso 4: Guardar avances (commits pequeños, no uno solo al final)

```bash
git add .
git commit -m "feat(ventas): agregar validación de stock en checkout"
```

Repite este paso varias veces durante la tarea cada avance lógico es un commit, no esperes a terminar todo.

### Paso 5: Subir tu rama a GitHub

```bash
git push origin feature/ventas-checkout
```

La primera vez que subes una rama nueva, Git puede pedirte:

```bash
git push --set-upstream origin feature/ventas-checkout
```

Es normal, solo dice "esta rama local ahora está conectada con esta rama remota".

### Paso 6: Abrir el Pull Request

Desde GitHub (o con `gh pr create` si tienen instalado GitHub CLI):

```bash
gh pr create --base develop --head feature/ventas-checkout \
  --title "Implementar validación de stock en checkout" \
  --body "- Valida stock disponible antes de confirmar venta
- Conecta con /api/ventas/validar-stock
- Cierra #12"
```

### Paso 7: Después de que aprueban y hacen merge

```bash
git switch develop
git pull origin develop
git branch -d feature/ventas-checkout          # borra la rama en tu máquina
git push origin --delete feature/ventas-checkout   # borra la rama en GitHub
```

## 3. Mantener tu rama al día sin perder tu trabajo

Si tu rama lleva más de un día abierta y `develop` avanzó mientras tanto, tráete esos cambios antes de que se acumule la diferencia:

```bash
git switch develop
git pull origin develop
git switch feature/ventas-checkout
git merge develop
```

Esto trae lo nuevo de `develop` a tu rama y crea un commit de fusión. Es la forma más segura úsala por defecto.

Si ya se sienten cómodos con Git y quieren un historial más limpio (sin commits de fusión), pueden usar `git rebase develop` en su lugar. Pero con una regla que no se negocia:

> **Nunca hagas rebase de una rama que ya subiste y que otro compañero también bajó o está usando.** Rebase reescribe el historial si alguien más ya tiene la versión vieja, se genera un desastre de conflictos. Rebase solo en ramas que son 100% tuyas y nadie más tocó.

---

## 4. Resolver conflictos de fusión

Cuando `git merge` o `git pull` avisan un conflicto:

```bash
git status
```

Muestra qué archivos están en conflicto. Ábrelos y busca estas marcas:

```
<<<<<<< HEAD
tu versión del código
=======
la versión que viene de develop
>>>>>>> develop
```

Edita el archivo dejando el código correcto (puede ser una versión, la otra, o una combinación), borra las marcas `<<<<<<<`, ` ======= `, `>>>>>>>`, y luego:

```bash
git add <archivo-que-resolviste>
git commit
```

Si te confundiste y quieres empezar de nuevo el merge:

```bash
git merge --abort
```

(o `git rebase --abort` si el conflicto vino de un rebase).

## 5. Deshacer errores sin dañar el trabajo de nadie

|Situación|Comando|
|---|---|
|Cambié un archivo y quiero descartarlo (sin commitear)|`git restore <archivo>`|
|Hice `git add` de más y quiero sacarlo del stage (sin perder el cambio)|`git restore --staged <archivo>`|
|Quiero deshacer mi último commit pero mantener los cambios|`git reset --soft HEAD~1`|
|Un commit ya compartido (pusheado) tenía un error|`git revert <hash-del-commit>`|
|Necesito cambiar de tarea rápido sin commitear lo que tengo a medias|`git stash` (y luego `git stash pop` para recuperarlo)|

Regla de oro: **`git reset --hard` y `git push --force` están prohibidos en ramas que ya compartiste con alguien más.** Reescriben o borran historia si otro compañero ya bajó esa rama, le rompes su copia local sin que se entere.

## 6. Revisar tu rama antes de abrir el Pull Request

```bash
git log --oneline develop..HEAD     # qué commits tiene tu rama que develop no tiene
git diff develop                    # todo el cambio acumulado, de una vez
```

Si el `git diff` muestra cosas que no tienen que ver con tu tarea (archivos de configuración del editor, `console.log` de prueba, etc.), límpialo antes de subir el PR hace la revisión más rápida para tu compañero.
