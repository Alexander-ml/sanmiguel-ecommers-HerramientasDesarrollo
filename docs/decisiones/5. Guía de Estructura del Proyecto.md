## 0. Vista general la raíz de cada repositorio

```
sanmiguel/
├── backend/
├── frontend/
├── infra/
├── docs/
├── .gitignore
└── README.md
```

Cuatro carpetas, cuatro responsabilidades. Nada de negocio va suelto en la raíz.

---

## 1. `backend/`

## Qué es cada paquete de nivel superior

| Paquete | Qué es |
|---|---|
| `config/` | Configuración técnica de Spring: seguridad, CORS, Swagger. No tiene lógica de negocio |
| `common/` | Código compartido por todos los módulos: manejo global de errores, utilidades |
| `auth/` | Módulo de negocio de usuarios y login incluye la seguridad ligada al Usuario (JWT) |
| `<módulo de negocio>/` | Un paquete por cada módulo (`inventario/`, `ventas/`...), mismo patrón de capas siempre |

## Árbol (dentro de cada módulo: `ventas/`, `inventario/`, etc.)

```
<módulo>/
├── controller/
├── service/
├── repository/
├── entity/
├── dto/
├── mapper/
└── exception/
```

## Qué es cada capa

|Capa|Qué es|
|---|---|
|Controller|Recibe la petición HTTP y devuelve la respuesta|
|Service|Contiene la lógica de negocio|
|Repository|Accede a la base de datos|
|Entity|Representa una tabla|
|DTO|Forma de los datos que entran/salen por la API|
|Mapper|Convierte entre Entity y DTO|
|Exception|Errores propios del módulo|

## Regla de flujo

`Controller → Service → Repository → base de datos`, y de vuelta. Un módulo nunca usa el Repository de otro módulo si necesita algo de otro módulo, llama a su Service.

## Convenciones de nombres

| Elemento    | Convención             | Ejemplo                      |
| ----------- | ---------------------- | ---------------------------- |
| Controller  | `<Entidad>Controller`  | `VentaController`            |
| Service     | `<Entidad>Service`     | `VentaService`               |
| Repository  | `<Entidad>Repository`  | `VentaRepository`            |
| DTO entrada | `<Entidad>RequestDTO`  | `VentaRequestDTO`            |
| DTO salida  | `<Entidad>ResponseDTO` | `VentaResponseDTO`           |
| Mapper      | `<Entidad>Mapper`      | `VentaMapper`                |
| Excepción   | `<Problema>Exception`  | `StockInsuficienteException` |

## Qué es cada carpeta/archivo

| Elemento             | Qué es                                                                                |
| -------------------- | ------------------------------------------------------------------------------------- |
| `main.tsx`           | Punto de entrada, monta la app en el HTML                                             |
| `App.tsx`            | Componente raíz, define el layout general                                             |
| `api/client.ts`      | Instancia de axios con interceptores (JWT automático, manejo de 401)                  |
| `api/generated/`     | Tipos y cliente HTTP generados automáticamente desde el backend nunca se edita a mano |
| `features/<módulo>/` | Código propio de cada módulo: sus componentes, hooks y tipos                          |
| `store/`             | Estado de cliente puro (Zustand) nunca datos del servidor                             |
| `components/`        | Componentes compartidos entre varios módulos                                          |
| `router/`            | Define las rutas de la aplicación                                                     |
| `mocks/`             | Respuestas falsas del backend, para desarrollar sin depender de él                    |
| `styles/`            | Estilos globales                                                                      |
| `public/`            | Archivos estáticos tal cual (imágenes, favicon)                                       |
| `Dockerfile`         | Construye la imagen de producción                                                     |
| `package.json`       | Dependencias y scripts del proyecto                                                   |
| `vite.config.ts`     | Configuración del build tool                                                          |

## Dentro de cada `features/<módulo>/`

| Elemento      | Qué es                                                   |
| ------------- | -------------------------------------------------------- |
| `components/` | Piezas visuales de ese módulo                            |
| `hooks/`      | Lógica reutilizable llamadas a la API con TanStack Query |
| `types.ts`    | Tipos propios de ese módulo                              |

## Regla de flujo

`Componente → hook (TanStack Query) → api/generated → backend`. El estado de servidor nunca se guarda en Zustand; el estado de cliente nunca se pide al backend.

## Convenciones de nombres

|Elemento|Convención|Ejemplo|
|---|---|---|
|Componente|PascalCase|`Carrito.tsx`|
|Hook|camelCase con prefijo `use`|`useVentas.ts`|
|Store|camelCase, prefijo `use` y sufijo `Store`|`useAuthStore.ts`|
|Tipo|PascalCase|`VentaResponse`|
## 3. `infra/`

## Árbol

```
infra/
├── docker-compose.yml
├── .env.example
├── .env
└── scripts/
    ├── sync-frontend.sh
    └── sync-backend.sh
```

## Qué es cada archivo

| Archivo              | Qué es                                                               |
| -------------------- | -------------------------------------------------------------------- |
| `docker-compose.yml` | Define y conecta los 3 servicios: base de datos, backend, frontend   |
| `.env.example`       | Plantilla de variables de entorno, sin datos reales sí se sube a Git |
| `.env`               | Variables reales (contraseñas) nunca se sube a Git                   |
| `scripts/`           | Scripts para sincronizar carpetas entre repositorios                 |

## Regla

Solo configuración y despliegue va acá nunca código de la aplicación (eso es `backend/` y `frontend/`).

## 5.Base de Datos

## Árbol

```
backend/src/main/resources/db/
├── migration/
│   ├── V<fecha>__crear_tabla_productos.sql
│   ├── V<fecha>__agregar_indice_sku.sql
│   └── R__cargar_categorias_iniciales.sql
└── seed-dev/
    └── R__productos_de_prueba.sql
```

## Tipos de archivo

| Tipo             | Qué es                                                                  | Cuándo se aplica                                                        |
| ---------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `V` (versionado) | Cambio de estructura: crear tabla, agregar columna, agregar restricción | Una sola vez, para siempre nunca se repite ni se edita después          |
| `R` (repetible)  | Datos de referencia que deben existir siempre (categorías base, roles)  | Cada vez que el contenido del archivo cambia, se vuelve a ejecutar solo |
| `seed-dev/`      | Datos falsos, solo para probar en tu máquina                            | Solo bajo el perfil `dev`, nunca en Docker/producción                   |
## Convención de nombres

| Tipo | Formato                            | Ejemplo                                    |
| ---- | ---------------------------------- | ------------------------------------------ |
| `V`  | `V<yyyyMMddHHmm>__descripcion.sql` | `V202609011430__crear_tabla_productos.sql` |
| `R`  | `R__descripcion.sql` (sin fecha)   | `R__cargar_categorias_iniciales.sql`

## Cómo se aplica todo esto

Flyway escanea `migration/` (y `seed-dev/` si el perfil es `dev`) cada vez que el backend arranca, y ejecuta lo que falte, en orden, solo.

## Regla

Cada tabla tiene un solo módulo dueño. Otro módulo nunca crea ni modifica esa tabla directamente la consulta a través del Service dueño.
