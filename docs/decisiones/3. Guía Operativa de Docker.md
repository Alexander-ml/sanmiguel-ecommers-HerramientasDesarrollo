## Referencia rápida

```bash
# Levantar (primera vez o con cambios de código)
docker compose up --build

# Levantar (días normales)
docker compose up

# Estado y salud de los contenedores
docker compose ps

# Logs
docker compose logs backend
docker compose logs -f backend
docker compose logs --tail=50 backend

# Reiniciar un servicio
docker compose restart backend

# Detener (sin borrar datos)
docker compose down

# Borrar todo, incluyendo la base de datos
docker compose down -v

# Limpiar espacio en disco
docker system prune
```

## 1. Por qué documentamos así los principios detrás de cada regla

**La configuración vive en variables de entorno, nunca en el código.** Es el tercer principio de la metodología _12-Factor App_ (el estándar de facto para apps que corren en contenedores desde hace más de una década): usuario, contraseña y URL de base de datos jamás se escriben directo en `application.yml` ni en el código se leen de variables de entorno, que vienen del `.env`. Así el mismo build corre en tu laptop, en la laptop de tu compañero, o en un servidor real, sin tocar una sola línea de código, y las credenciales nunca terminan commiteadas en Git por accidente.

**Un servicio "corriendo" no es lo mismo que un servicio "listo".** Que el contenedor de MySQL diga `running` no significa que ya acepta conexiones puede seguir inicializando la base de datos por dentro. Por eso usamos `healthcheck` en cada servicio y `depends_on: condition: service_healthy`: el backend no arranca hasta que Docker confirmó, con una prueba real, que MySQL ya responde no solo que el contenedor existe. Esto evita el error clásico de "el backend no conecta a la base de datos" que en realidad es solo un problema de orden de arranque.

**Las imágenes se reconstruyen solo cuando cambia el código, y nunca se editan a mano.** Una imagen construida es inmutable: si necesitas otro comportamiento, se reconstruye desde cero (`--build`), nunca se entra al contenedor a parchar algo manualmente. Esto es lo que garantiza que lo que funciona en tu máquina funcione igual en la de cualquier otro.

**Los Dockerfile son multi-stage: Maven y Node.js no viajan a la imagen final.** El backend se compila en una etapa que sí tiene Maven instalado, pero la imagen que finalmente corre solo lleva el `.jar` ya compilado sobre un runtime de Java liviano. Mismo criterio para el frontend: Node.js compila los archivos estáticos, pero lo que corre en el contenedor final es Nginx sirviendo esos archivos no Node.js. Imágenes más chicas, más rápidas de levantar, y con menos herramientas instaladas que representen una superficie de ataque innecesaria.

## 2. Antes de empezar requisitos

| Requisito                    | Cómo verificar                                                |
| ---------------------------- | ------------------------------------------------------------- |
| Docker Desktop instalado     | `docker --version` en una terminal                            |
| Docker corriendo             | El ícono de Docker en la barra de tareas está activo          |
| Archivo `.env` en `infra/`   | Debe existir `infra/.env`, copiado desde `infra/.env.example` |
| Terminal abierta en `infra/` | Ahí vive el `docker-compose.yml`                              |

Si no tienes el `.env`, cópialo del ejemplo y complétalo con las credenciales que te pase quien lidera infraestructura nunca inventes tus propias credenciales de producción ni las compartas por chat sin cifrar.

## 3. Arrancar el proyecto

### Primera vez, o cuando cambió el código

```bash
docker compose up --build
```

Úsalo cuando: es la primera vez, alguien cambió backend/frontend, se actualizó `pom.xml` o `package.json`, o cambió un `Dockerfile`.

**Qué hace:** reconstruye las imágenes (Maven compila el backend, npm compila el frontend) y levanta los 3 contenedores en el orden correcto MySQL primero, backend cuando MySQL está realmente listo, frontend cuando el backend está realmente listo.

### Días normales, sin cambios de código

```bash
docker compose up
```

Levanta los contenedores con las imágenes que ya existen, sin recompilar.

### Qué deberías ver en consola si todo va bien

```
sanmiguel-database   | [Server] ready for connections
sanmiguel-backend    | Started BackendApplication in X seconds
sanmiguel-frontend   | /docker-entrypoint.sh: Configuration complete; ready for start up
```

### Cómo detener correctamente

```bash
docker compose down
```

**Nunca cierres la terminal directamente** los contenedores no se detienen limpio y puede quedar el puerto ocupado la próxima vez.

## 4. Comandos básicos del equipo

| Comando                                 | Cuándo usarlo                                                          |
| --------------------------------------- | ---------------------------------------------------------------------- |
| `docker compose ps`                     | Ver qué contenedores están corriendo (y su estado de salud)            |
| `docker compose logs backend`           | Ver logs de un servicio puntual                                        |
| `docker compose logs -f backend`        | Seguir los logs en tiempo real (`Ctrl+C` para salir)                   |
| `docker compose logs --tail=50 backend` | Solo las últimas 50 líneas                                             |
| `docker compose restart backend`        | Reiniciar un servicio colgado sin apagar todo                          |
| `docker compose up --build`             | Reconstruir imágenes tras un cambio de código                          |
| `docker compose down -v`                | Borrar todo, **incluyendo los datos de la base** ver advertencia abajo |
| `docker stats`                          | Ver cuánto CPU/memoria usa cada contenedor                             |

> **Cuidado con `down -v`:** el `-v` elimina el volumen, o sea los datos de la base de datos. Úsalo solo cuando el sistema está completamente roto, quieres resetear la base desde cero, o te lo indica quien lidera infraestructura. Después: `docker compose up --build`.

## 5. Validación del sistema 3 puntos, en orden

### 1. Base de datos

```bash
docker compose ps
```

`sanmiguel-database` debe aparecer `running` y, si el healthcheck ya corrió, `healthy`.

### 2. Backend

```
http://localhost:8080/actuator/health
```

```json
{
  "status": "UP",
  "components": {
    "db": { "status": "UP" },
    "diskSpace": { "status": "UP" }
  }
}
```

`"db": "UP"` confirma que el backend sí logró conectarse a MySQL, no solo que el proceso Java arrancó.

### 3. Frontend

```
http://localhost
```

Debe cargar la página del sistema, aunque esté incompleta.

|Qué verificar|URL / comando|Resultado esperado|
|---|---|---|
|Base de datos|`docker compose ps`|`sanmiguel-database` → `running` / `healthy`|
|Backend|`http://localhost:8080/actuator/health`|`{"status":"UP"}`|
|Frontend|`http://localhost`|Página carga|

## 6. Flujo de trabajo diario

### Inicio del día

|Paso|Acción|
|---|---|
|1|Abre Docker Desktop y espera a que inicie|
|2|Terminal en `infra/`|
|3|`git switch develop && git pull origin develop`|
|4|Decide `up` o `up --build` (tabla abajo)|
|5|Valida los 3 puntos de la sección 6|
|6|Empieza a trabajar|

### ¿Con `--build` o sin `--build`?

|Situación|Comando|
|---|---|
|Inicio del día, nadie cambió código|`docker compose up`|
|Cambió el backend o el frontend|`docker compose up --build`|
|Cambió `pom.xml` o `package.json`|`docker compose up --build`|
|Cambió un `Dockerfile`|`docker compose up --build`|
|Cambió solo `.env`|`docker compose down` → `docker compose up`|

**Regla del equipo:** en caso de duda, `--build`. Tarda más pero garantiza que el cambio se aplicó.

### Durante el día

- Backend en modo desarrollo (IntelliJ + Spring DevTools): reinicia automático con cada cambio guardado. Si no, `docker compose restart backend`.
- Frontend en modo desarrollo (VS Code + Vite): hot reload automático en el navegador, no hace falta tocar Docker.

### Fin del día

```bash
git add . && git commit -m "..." && git push
docker compose down
```
