## 1. Qué modelo seguimos y por qué

En la industria existen sobre todo tres modelos de ramas:

| Modelo                      | Cómo funciona                                                                                         | Para quién funciona mejor                                                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Trunk-based development** | Todos integran cambios pequeños directo a una sola rama principal, varias veces al día                | Equipos con mucha automatización (CI/CD) y alta confianza/autonomía entre desarrolladores senior                                                                                                |
| **Gitflow**                 | Varias ramas de larga vida (`main`, `develop`, `release`, `hotfix`) con control estricto por revisión | Equipos que necesitan control fuerte de lo que entra al código, o con integrantes con menos experiencia es el modelo recomendado cuando todo cambio debe pasar por revisión antes de integrarse |
| **GitHub Flow**             | Una sola rama estable (`main`) + ramas cortas por tarea que se despliegan seguido                     | Equipos chicos con despliegue continuo                                                                                                                                                          |

Nosotros usamos **una versión simplificada de Gitflow**: dos ramas permanentes (`main` y `develop`) más ramas temporales de corta duración. Es el modelo que mejor se adapta a un equipo donde todo cambio debe ser revisado por otra persona antes de integrarse justo nuestro caso.

Lo único que tomamos prestado del modelo trunk-based, porque en esto **todas** las empresas están de acuerdo sin importar el modelo que usen: **las ramas viven poco tiempo.** Mientras más días pasa una rama sin integrarse a `develop`, más conflictos de fusión genera y más difícil es revisarla. El objetivo es días, no semanas.

## 2. Ramas permanentes

|Rama|Contiene|Quién le hace push directo|
|---|---|---|
|`main`|Código estable, probado, listo para demostrar/entregar|**Nadie.** Solo llega por merge desde `develop`, en momentos de entrega|
|`develop`|La integración de todo el trabajo del equipo, siempre debe poder ejecutarse localmente|**Nadie.** Solo llega por merge de Pull Requests aprobados|

Si alguien necesita hacer push directo a `main` o `develop` sin pasar por un Pull Request, algo del proceso está fallando — no debería pasar nunca, salvo configuración inicial del repositorio.

## 3. Ramas temporales tipos y cuándo usar cada una

| Prefijo     | Para qué se usa                                                       | Nace de   | Se integra en          |
| ----------- | --------------------------------------------------------------------- | --------- | ---------------------- |
| `feature/`  | Funcionalidad nueva                                                   | `develop` | `develop`              |
| `fix/`      | Corrección de un bug encontrado durante desarrollo (no en producción) | `develop` | `develop`              |
| `hotfix/`   | Corrección urgente sobre algo que ya está en `main`                   | `main`    | `main` **y** `develop` |
| `refactor/` | Mejora interna del código sin cambiar comportamiento                  | `develop` | `develop`              |
| `docs/`     | Documentación (README, guías, comentarios de arquitectura)            | `develop` | `develop`              |
| `chore/`    | Mantenimiento: configuración, dependencias, Docker, scripts           | `develop` | `develop`              |
| `test/`     | Agregar o corregir pruebas                                            | `develop` | `develop`              |

No necesitamos `release/` por ahora lo incorporamos si en algún momento manejamos versiones paralelas del sistema en producción.

## 4. Convención de nombres _patrón exacto_

```
<tipo>/<módulo>-<descripción-breve>
```

Reglas duras:

- Todo en **minúsculas**, sin tildes ni ñ.
- Palabras separadas por **guion medio** (`-`), nunca espacios ni guion bajo.
- El `<módulo>` es uno de los módulos del sistema: `inventario`, `compras`, `ventas`, `tienda`, `clientes`, `auth` (Usuarios y Seguridad), `config` (Configuración General).
- Descripción breve y concreta — 3 a 6 palabras máximo, nada de `final`, `prueba`, `cosas`, `arreglos`.
- Si trabajan con Issues de GitHub, el número de issue va justo después del tipo: `feature/12-ventas-checkout`.

**Ejemplos correctos:**

```
feature/ventas-checkout
feature/inventario-alertas-stock-minimo
fix/compras-error-recepcion-mercaderia
hotfix/auth-token-expira-antes-de-tiempo
refactor/clientes-validacion-dni-ruc
docs/readme-configuracion-docker
chore/docker-healthcheck-mysql
```

**Ejemplos incorrectos (y por qué):**

```
juan-rama              → no dice qué hace, ni el tipo
Feature/Ventas         → mayúsculas, sin descripción
fix_bug                → guion bajo, sin módulo, sin contexto
prueba2                → no dice nada
```

## 5. Ciclo de vida de una rama

1. Se crea siempre desde `develop` **actualizado** (`git pull origin develop` antes de crear la rama).
2. Vive pocos días si una tarea va a tomar más de una semana, probablemente hay que partirla en tareas más chicas.
3. Commits pequeños y frecuentes, no un solo commit gigante al final.
4. Push a GitHub apenas hay avance guardable, no solo al terminar.
5. Pull Request hacia `develop` cuando la tarea está lista para revisión.
6. Revisión de otra persona del equipo (ver sección 7).
7. Merge solo después de aprobación.
8. Se elimina la rama, en local y en GitHub, inmediatamente después del merge.

## 6. Mensajes de commit Conventional Commits

Formato:

```
tipo(alcance): descripción imperativa breve
```

| Tipo       | Uso                                         |
| ---------- | ------------------------------------------- |
| `feat`     | Nueva funcionalidad                         |
| `fix`      | Corrección de bug                           |
| `refactor` | Mejora sin cambiar comportamiento           |
| `docs`     | Documentación                               |
| `test`     | Pruebas                                     |
| `chore`    | Mantenimiento, configuración, dependencias  |
| `perf`     | Mejora de rendimiento                       |
| `ci`       | Cambios en integración continua / pipelines |

El `alcance` es el módulo afectado (`ventas`, `inventario`, `auth`, `docker`, etc.). La descripción va en modo imperativo ("agregar", no "agregando" ni "agregué"), sin punto final.

```
feat(ventas): implementar validación de stock antes de confirmar venta
fix(caja): corregir cálculo de diferencia en cierre de caja
refactor(clientes): extraer validación de DNI/RUC a utils
docs(readme): actualizar instrucciones de configuración local
chore(docker): agregar healthcheck al contenedor de base de datos
```

## 7. Pull Requests

Prácticas tomadas directamente de cómo Google documenta su propio proceso de revisión de código:

- **PRs pequeños y enfocados en un solo objetivo.** Un PR que mezcla tres funcionalidades distintas es imposible de revisar bien. Si la tarea creció, se parte en varios PRs.
- **Título en modo imperativo**, igual que un commit: "Implementar checkout de ventas", no "Cambios en ventas".
- **Descripción que explique qué cambia y por qué**, no solo qué archivos se tocaron. 
	Ejemplo: Se agregó validación de stock antes de confirmar la venta- Se conecta con el endpoint /api/ventas/validar-stock- Cierra el issue #12
- **Siempre se asigna un revisor** nunca se aprueba el propio PR.
- El revisor evalúa, en este orden: **diseño** (¿tiene sentido dónde se puso esto?), **funcionalidad** (¿hace lo que dice que hace?), **complejidad** (¿se puede simplificar?), **pruebas**, **nombres claros** de variables/métodos, y **estilo**.
- Los comentarios que no son obligatorios para aprobar (sugerencias, mejoras opcionales) se marcan con el prefijo **`Nit:`** así el autor sabe que puede resolverlo después y no bloquea el merge.
- Cuando el PR está listo para integrarse, el revisor aprueba con **LGTM** ("Looks Good To Me").
- **Regla de tiempo:** un revisor responde dentro de un día hábil. Un PR nunca debería quedar "flotando" varios días sin que nadie lo mire.
- Si autor y revisor no se ponen de acuerdo en un comentario, se conversa directo (llamada rápida, no una guerra de comentarios), y si sigue sin resolverse, se escala al resto del equipo nunca se deja un cambio trabado indefinidamente por un desacuerdo.

## 8. Qué está prohibido

```
push directo a main
push directo a develop
commits llamados "cambios", "arreglos", "wip"
trabajar todos en la misma rama
borrar ramas ajenas sin avisar
aprobar tu propio Pull Request
merge sin al menos una revisión
dejar un Pull Request más de 2-3 días sin revisar
```

|---|---|---|---|

|Corregir un bug (no en producción)|`develop`|`fix/`|`fix/inventario-stock-negativo`|
|Corregir algo urgente ya entregado|`main`|`hotfix/`|`hotfix/auth-sesion-no-expira`|
|Mejorar código sin cambiar comportamiento|`develop`|`refactor/`|`refactor/ventas-servicio-pago`|
|Documentación|`develop`|`docs/`|`docs/api-openapi-ventas`|
|Configuración / mantenimiento|`develop`|`chore/`|`chore/env-variables-mysql`|
